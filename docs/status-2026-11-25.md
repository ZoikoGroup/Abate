## 2. Step 1 — Test Reporting Bug (`passed > total`) Root Cause & Fix

### Root Cause
1. In `backend/tools/test-phase4-control.ts`, `backend/tools/test-phase5-retention.ts`, and `backend/tools/test-phase7-planes.ts`, the initial fixture-seeding call (`Setup: Seed isolated two-tenant environment`) was invoked through `runTest(...)`, which incremented `passed++`. The summary line then hardcoded only the numbered test count (`/8`, `/9`, `/5`), producing impossible counts **`9/8`**, **`10/9`**, and **`6/5`**.
2. `backend/tools/test-phase6-ai.ts` worked around the same defect with `${passed - 1}/14` (fragile against test additions), while `test-phase2-ingestion.ts` and `test-reconstruction.ts` hardcoded `/10` and `/9` (inflating counts by counting Setup as a test).
3. `backend/tools/build-dossier.ts` (`countPassingChecks`) counted every `✔` glyph in stdout, which double-counted both Setup lines and summary lines beginning with `✔ Completed ...`, inflating `testsPassed` in `evidence/release-dossier.json` (e.g., `11` for retention instead of `9`, `16` for AI instead of `14`, `7` for planes instead of `5`).

### Fix Applied
- Added a dedicated `runSetup(...)` helper (logs `[setup]` without `✔` and does not increment test counters) and dynamic `total++` / `passed++` tracking inside `runTest(...)` with `assert.strictEqual(passed, total)` in all six phase suites:
  - `backend/tools/test-phase2-ingestion.ts` → **`9/9`**
  - `backend/tools/test-reconstruction.ts` → **`8/8`**
  - `backend/tools/test-phase4-control.ts` → **`8/8`** (was `9/8`)
  - `backend/tools/test-phase5-retention.ts` → **`9/9`** (was `10/9`)
  - `backend/tools/test-phase6-ai.ts` → **`14/14`** (was `${passed - 1}/14`)
  - `backend/tools/test-phase7-planes.ts` → **`5/5`** (was `6/5`)
- Updated `backend/tools/build-dossier.ts` (`countPassingChecks`) to parse `passed/total` summaries first, fail the suite if `passed > total`, and exclude summary `✔ Completed/Live/Built` lines from fallback counting.

## 3. Step 2 — Live PostgreSQL 16.2 Verification Summary (Non-Superuser Runtime Roles)

Running against live `postgres:16.2-alpine` with non-superuser `abate_migrator` (`rolsuper=f, rolbypassrls=f, rolcreaterole=f, rolcreatedb=f`) exposed **four real live-PostgreSQL defects** that had been hidden under `memDb` and/or GitHub Actions superuser Postgres:

1. **`backend/db/init/01-roles.sql`**: Missing `abate_privacy` caused `0082_phase3_privacy_roles.sql` to fail on fresh non-superuser Postgres with `permission denied to create role`, leaving `0082`–`0089` unapplied. **Fixed** by pre-creating `abate_privacy` with `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`.
2. **`backend/tools/test-worker-crash-lab.ts` (Tests 8 & 9)**: Seeded and cleaned up `outbox_event` rows as `abate_worker`, which live PostgreSQL rejected (`permission denied for table outbox_event`) and migration `0089` RLS restricted to `PUBLISHED` rows. **Fixed** by seeding via `withTenant` (`abate_app`) and cleaning up non-published rows via `migratorPool` when PG is live.
3. **`backend/db/migrations/0090_migrator_metric_definition_policy.sql`** (new bug-fix migration): Under `FORCE ROW LEVEL SECURITY` with non-superuser `abate_migrator`, `metric_definition` had no `INSERT` policy for `abate_migrator`, and operational views `ops_active_tenants` (`0087`) and `ops_connector_health` (`0088`) returned `0` rows because `abate_migrator` had no `SELECT` policy on `tenant` or `connection`. **Fixed** by adding scoped `TO abate_migrator` policies on `metric_definition`, `tenant`, and `connection` while keeping runtime roles (`abate_app`, `abate_ops`, `abate_worker`, etc.) strictly restricted with zero direct grants.
4. **`backend/tools/test-pg-parity.ts`**: `audit_event_immutable` probe and `outbox_event` cleanup ran outside a transaction with `app.tenant_id` unset, so `FORCE RLS` hid rows from non-superuser `abate_migrator` before triggers fired. **Fixed** by wrapping both in transaction-local `set_config('app.tenant_id', $1, true)`.
